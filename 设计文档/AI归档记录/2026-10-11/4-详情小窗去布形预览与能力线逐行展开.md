## 五、实量复核（探针 135 / 137 / 139 / 142）

### 1. 文案朝哪边长（决定会不会顶到名字行）

`Txt_DetailDesc` 是 `pivot=(0,1)` 且锚在窗顶，顶边钉在 `y=-62`，所以加高只往下走，**不会顶到上面的名字行**；`Img_Face` 与 `Img_Accent` 都吃拉伸，窗子长高时底与色条一起跟上。

同一枚 MaoKen 22 实测：1 行 = 120×22，4 行 = 352×88（每行 22，行距不额外吃高）。

### 2. 全量数据扫一遍有没有撞宽度兜底

拿 `ClothCatalog.asset` 里每块布 × 它自己的每个异形，再加 `Items/` 下全部装备道具的每一档，共 **87 条**真实文案逐条实量：

| 指标 | 结果 |
| --- | --- |
| 多于一行的 | 6 条（顺流布的两块异形各 3 行） |
| 需求宽超过 `DETAIL_MAX_WIDTH=720` 的 | **0 条**，最宽的一条是空白布 422 |
| 三条能力线的布展开后 | 窗宽 386，窗高 132 → 159 |

再把灰字提示单独量了一遍（负载那条最坏情况）：最长「这种布的载量已经吃满，再买一块不会加载量」实宽 440，加留白与价钱预留 = 664，仍在 720 内。四条文案叠满时窗高 181。

结论：720 这个上限现在是纯兜底，够不着；`Overflow` + 不折行 + 窗宽按实量走，三者一起把「…」这个 bug 从根上堵死，而不是靠把上限调大。

### 3. 落点会不会因为窗子变高而顶出安全区

`refreshDetailWindow` 与 `detailAnchor` 两条排布路径本来就按 `m_detailHeight` 算半高与六个候选位，窗子长高后夹回安全区的边界跟着一起长，不需要额外改。

### 4. 编译与运行时字面量

`compiling=False updating=False playing=False`，反射读回 `SEPARATOR` = `[LF]`，`UIShopBuffText.OfMany` 解析正常。工程无新报错（控制台剩下的两条 11:09 的报错是我自己一个探针脚本写错（`List<>` 忘了 using） 引起的，与工程无关）。
