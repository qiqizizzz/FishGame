# 一、定位与主循环

一句话：**用背包 build 决定你能钓多深、能带回几条；用下潜验证这个 build。**

参考原型是《背包战斗》的网格背包 + 商店 + 合成，但把它的"自动战斗"换成**实时钓鱼**。这个替换是本设计的立身之本，见 2.2。

```text
  ┌──────────────────────────────────────────────────────┐
  │  第 n 回合 · 钓鱼阶段（固定 3 次下潜，唯一的实时技巧环节）│
  │     LineLength    = 能到多深（硬上限，不是倒计时）      │
  │     TensionMax    = 能拖多大的鱼（本版不做断线）        │
  │     MaxCarryCount = 钩上能挂几条（名额，见 2.2）        │
  └───────────────────────┬──────────────────────────────┘
                          ↓
      每一潜出水：渔获按 01 的 3.5 公式算价值 → 计入回合进度与金币银行
                          ↓
      三次打满 → 回合裁决：本回合渔获价值 ≥ 本回合目标？
           ├─否──► 封盘结算，本局结束（再来一局回到第 1 回合）
           └─是──► 金币留下，目标 ×1.8，进入商店阶段
                          ↓
      商店阶段（每回合 1 次）：金币 → 钓竿（主武器）+ 藏品（BUFF）
                  背包整备：网格 · 可旋转 · 3 同合成升品质
                          ↓
      整备完毕 → 回到钓鱼阶段，开第 n+1 回合
                          ↓
      达成里程碑 → 解锁下一座岛（新鱼 + 新商品进奖池）
```

回合口径（与 01 的 3.4 一致）：

- 每回合固定 3 次下潜，**次数本身不做成可升级数值**——背包升的是线长、名额、价值倍率，不是潜次
- 空手出水照样扣次数，避免反复起竿刷回合
- 中途达标不提前收尾，三次打满才裁决
- 金币跨回合保留（银行）；回合目标每回合重算，超额渔获只进银行，不垫高下一回合目标
- 商店每回合都进：先进商店整备，再进下一回合钓鱼

# 二、两条已定的方向性决策

## 2.1 全程竖屏（1080x1920）

| 依据 | 说明 |
| --- | --- |
| **深度分辨率翻倍（决定性）** | 同一套正交相机下，横屏把 100 m 摊在 1080 px 上 = **10.8 px/m**；竖屏摊在 1920 px 上 = **19.2 px/m**。玩法核心是垂直纵深，横屏等于把最重要的信息轴压缩一半 |
| 横向空间对钓鱼无收益 | 玩家不需要左右看，只需要看"下面还有什么" |
| 面试官预期锚点 | 题目录屏是 632x1264 竖屏 |
| 厂商取向 | 点点互动主做手游，竖屏是休闲市场默认 |
| 网格背包在竖屏放得下 | 940 宽的面板做 5 列 = **每格 156 px**（26 px 底图的 6 倍整数放大，不放糊），比同类竖屏网格背包（《咸鱼之王》《疯狂骑士团》）宽松，图标 + 名称够用 |

**禁止混用朝向**（钓鱼竖屏 / 背包横屏）。转屏会直接打断手感连贯性，更要紧的是会逼出两套 `CanvasScaler` 与两套适配逻辑，污染整个 UI 架构——这恰好是题目第 1 条要看的东西。

参考图那种"左背包右商店"是横屏专属排版，竖屏改为上下分栏，见第四章。

## 2.2 渔获不占背包格，改用条数名额

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 渔获进背包网格 | **放弃** | 会制造**第二个空间解谜**。下潜时的紧张感本该是"这条鱼张力快断了，我赌不赌"，一旦渔获要占格子，紧张感就退化成"我格子还够不够"。两个空间决策互相稀释 |
| 条数名额 | **采用** | 保留"带回哪几条"的真决策，零空间管理成本。且天然承接"增加钓竿可携带数量"这条升级线 |

**携带名额规则**（`FishDataSO` 不再持有 `CarryCost` 字段，携带成本与体型彻底解耦）：

| 口径 | 规则 |
| --- | --- |
| 名额上限 | `IFishingStats.MaxCarryCount`，钩子配置字段 `CarryCountCeiling`，当前 10；HUD 负载行显示为 `0 / 10` |
| 单条占用 | 一律 **1 个名额**，与体长、稀有度无关，任何鱼都钓得起来 |
| 能钓到什么 | 由鱼线长度锁定的深度带决定：浅层只有低级鱼，线长了才够得到高级鱼 |
| 钩满之后 | `CanAttach` 返回 false，回收途中新鱼从钩下穿过，不再挂新鱼 |
| 河豚 | 障碍，碰即受罚并按概率甩掉已挂的鱼，本身不占名额、不参与携带结算 |

初始 `MaxCarryCount = 10`。含义：一次回收最多带 10 条上水面，**带哪 10 条**才是决策点——
金枪鱼和金鱼占完全相同的名额，取舍从「容量够不够」变成「同样的名额换多少金币」，这正是 build 与战利品之间的耦合点。
扩容线（`MaxCarryCount` +N）依旧由钓竿、鱼篓类藏品提供。

# 三、`IFishingStats`：整个扩展层的唯一接口

这是本篇最重要的一条架构约束。**下潜层不允许读任何背包概念**，只读一个由背包聚合出来的只读属性包。

```text
背包物品 ──(Apply)──> IFishingStats ──(消费)──> 下潜 / 张力 / 生成 / 结算
```

| 字段 | 类型 | 初始值 | 谁能改 | 玩法含义 |
| --- | --- | --- | --- | --- |
| `LineLength` | float (m) | 25 | 钓竿、线轮类藏品 | **能到多深**。硬上限，钩子顶到线头而下方仍有鱼 = 核心挫败感来源 |
| `MaxCarryCount` | int | 10 | 钓竿、鱼篓类藏品 | 钩上能挂几条（见 2.2） |
| `ReelSpeed` | float (m/s) | 4.5 | 卷线器类藏品 | 收线速度，影响"大鱼能不能拖到水面" |
| `TensionMax` | float | 100 | 钓竿、握把类藏品 | 张力上限，超过即断线 |
| `TensionRelief` | float (0–1) | 0 | 缓震类藏品 | 断线前的缓冲窗口比例 |
| `LurePull` | float | 1.0 | 饵料消耗品 | 稀有度权重放大系数，作用于加权随机表 |
| `DetectRadius` | float | 0.8 | 探照灯类藏品 | 鱼显形半径，深水区关键 |
| `CoinBonus` | float (0–1) | 0 | 藏品 | 卖鱼金币加成，**上限锁 0.6** |

**聚合方式**：背包内物品按「钓竿优先、藏品按格坐标行主序」依次 `Apply(stats)`，产出不可变结构体，出水与整备时各重算一次。**不做增量缓存**——背包物品最多二十来件（受可用格数封顶），全量重算是纳秒级，换来零状态同步 bug。

# 四、竖屏三栏布局（尺寸定稿）

基准 1080x1920，`CanvasScaler` = ScaleWithScreenSize / 1080x1920 / Match 0.5。

| 区域 | 屏幕矩形 (y 自顶向下) | 内容 | 备注 |
| --- | --- | --- | --- |
| 标题 | 80 – 170 | 「商店 · 背包」 | 高 90，字号 60 |
| 状态条 | 194 – 314 | 金币 / 回合目标进度 / 剩余下潜次数 | `Panel_Info` 940x120 |
| 背包 | 338 – 1228 | 5 列 x 5 行容器 | `Panel_Backpack` 940x890；`Grid_Slots` 812x812 居中，每格 **156x156**，间距 8；网格之上叠一层等大的 `Layer_Items` 画跨格物品 |
| 仓库 | 1240 – 1422 | 一排 5 格暂存 | `Panel_Storage` 940x182；`Grid_Storage` 568x104，每格 104x104，间距 12 |
| 商店 | 1434 – 1662 | 一排 4 张商品卡 + 刷新按钮 | `Panel_Shop` 940x228；`Row_Goods` 868x150，单卡 202x150；`Btn_Refresh` 150x48 贴面板右上 |
| 行动按钮 | 1680 – 1840 | 「开始下潜」520x160 + 「关闭」320x160 | 底锚定，距屏幕底 80 |

五格一行 = 156 x 5 + 间距 8 x 4 = 812，网格宽高相等，**格子是正方形**。竖向预算：标题与状态条占到 314，行动按钮自 1680 起，中间 338 – 1662 整段给背包 / 仓库 / 商店三块面板，面板之间留 12。格数或行数再涨时优先压格子（156 → 140 一档），状态条与行动按钮的位置不动。

底板统一用 `Setting menu_1` 以 **Sliced** 拉伸（走九宫格切边，四角不糊），长条与按钮用 `Button_long`，空格子用 `Square Buttons 26x26_1`。

**锁定格与跨格物品都不用贴图**：锁定格是 `sprite = null` 的纯色暗块（`#6E5F45`），跟参考图「黑色剪影」一致，解锁后换成空格底图；跨格物品由 `UIShopItemView` 按形状格逐格铺纯色方块，方块边长含 8 px 格间距（pitch = 164），相邻两块严丝合缝连成一整块，底色是品质色压暗 28% 当暗边、内缩 4 px 的亮面是品质色本身。全程纯色 rect，不吃贴图缩放，不会出现像素糊边。仓库格整格染品质色并标名称，名称色按底色亮度自动切深棕 / 浅米。共享贴图的 PPU 一律不动，改一处会牵动其他界面。

编辑器菜单 `Tools/钓鱼游戏/预览 商店背包面板` 可直接看版式：Play 模式走 `UIManager` 正常打开，Edit 模式只往场景里摆一份实例供目视，不写回场景文件。

版式改动只走 `Tools/钓鱼游戏/重建 商店背包面板版式`（`UIShopPanelBuilder`）：它删掉并重建上面三块面板，把数值一次性写进预制体，标题、状态条、行动按钮三块保持手工状态不受影响。格子边长与间距在运行时由 `UIShopPanel` 从 `GridLayoutGroup` 读，改版式不动脚本。

# 五、背包网格系统（题目第 1 条的主战场）

| 结构 | 选型 | 为什么这么选 |
| --- | --- | --- |
| 网格占用 | **`long` 位图**（每行 8 位，位序 = 行 x 8 + 列；容器 5x5 = 25 格，开局只点亮锚形 7 格、其余锁定） | 放置校验 = 一次 `位与`；旋转 = 查预计算掩码表。每行留 1 位余量是为了整张位图一次左移就能平移，不必逐行修正跨行串位；行列上限 7 时最高位 54，仍在符号位之内。比 `List<RectInt>` + 逐个 AABB 相交干净一个数量级，且是"数据结构应用"最直接的展示位 |
| 解锁范围 | 位图分「容器掩码」与「已解锁掩码」两层，锁定格 = 容器有格但未解锁；解锁掩码按**阶段**存在 `BackpackConfigSO.UnlockMaskList`，运行时 `UnlockMaskAt(stage)` 取用 | 扩背包 = 推进解锁阶段换一张掩码，不改容器尺寸。**开局异形已定稿**（见 5.1），格子是空格还是锁格全由掩码说话，早期那版「中心 3x3 占位」已作废 |
| 物品形状 | **形状模板库** `Assets/Data/Backpack/Shapes`，一个模板一份 `GridShapeSO`（只存 `MaskBits` 位图，朝向算一次缓存） | 形状是「模板」不是「道具身份」，多个道具、多个档位共用同一模板；格数由形状资产推导，配置里不再手写容量数字（见 5.2） |
| 旋转 | 形状点集 `(x,y)→(y,-x)` 归一化后**预计算 4 个朝向**缓存 | 运行时零计算；位图侧用同一张朝向表做 `>>` 位移 |
| 落位校验 | `mask & occupied == 0 && (mask & gridMask) == mask` | 一行表达式同时完成越界与重叠检测 |
| 物品定义 | `BackpackItemSO`：`Id` / 名称 / 图标 / `BackpackStatMod`（能力线 + 数值）/ `TierShapes`（每档一个形状模板）/ `TierValues`（每档一个数值）/ 售价 | **档位 = 品质**，升档同时换形状与数值；数据驱动，新增物品零改代码 |
| 合成规则 | `SynthesisRuleTableSO`（输入品质 + 数量 + 形状 → 输出），**规则表驱动** | 禁止 if-else 硬编码品质链；策划可改 |
| 快速合成 | 全表扫描 `Dictionary<synthKey, List<slot>>`，数量 ≥ 3 即高亮 | 参考图左上「快捷合成」按钮 |
| 商店库存 | 岛屿解锁池 + 权重表 + **保底计数器** | 连续 N 潜不出高品质则强制插入，防极端脸黑 |
| 三选一 | 条件过滤器链（`ICardFilter` 串接）+ 加权抽取 | 责任链 + 策略，两个模式同一处落地 |

只保留 5 个模板，`T`、`S` 与单格全部砍掉，最大 6 格封顶 —— 竖屏格子本就小，大形状和「随便塞一格」的碎片都会把取舍感冲淡：

# 六、品质与合成

**品质链白 → 蓝 → 紫 → 金直接复用已落地资产**，零新增成本：

| 品质 | 复用对象 | 颜色 |
| --- | --- | --- |
| 白 | `Mat_Fish_Common` / `T_Fish_Mod_Common` | `#C9CDD2` |
| 蓝 | `Mat_Fish_Rare` / `T_Fish_Mod_Rare` | `#3E7BFA` |
| 紫 | `Mat_Fish_Epic` / `T_Fish_Mod_Epic` | `#8B5CF6` |
| 金 | `Mat_Fish_Legendary` / `T_Fish_Mod_Legendary` | `#F5B93B` |

即 `RarityTableSO` 同时服务三处：鱼身配色、结算 UI、**背包物品品质边框与角标**。颜色与数值同源，符合 01 第 3.6 节"杜绝硬编码散落"。

合成规则（待数值细化，先定形）：

- **3 个同品质 + 同 synthKey 的物品 → 1 个高一品质**，形状**可变**（默认继承输入中最大者）
- 跨类不合成（钓竿线与藏品线各自成链）
- 金品质为顶，不再合成
- `Uncommon` 档（`#4CAF7D` 绿）在本篇**不启用**，保留给"特殊功能藏品"作区分色，避免与四档链混淆

> 注意：01 第 3.6 节的五档稀有度描述的是**鱼的价值档位**，本篇四档描述的是**物品品质档位**，两套语义不同但共用同一张 `RarityTableSO` 的配色。实现时用两个独立枚举（`FishRarity` / `ItemQuality`），靠映射表关联，**不要复用同一个枚举**。

# 七、岛屿分层与永久解锁

这一章是肉鸽平衡的生死线，必须守住一条铁律。

| 层 | 内容 | 是否跨局保留 | 例子 |
| --- | --- | --- | --- |
| **run 内推进** | 当前潜到第几座岛、背包里的物品、金币 | **否，每局重置** | 第 3 潜达标 → 本局解锁第二座岛 |
| **永久解锁** | **内容池**：哪些鱼种、哪些物品会进入随机奖池 | 是 | 首次钓到皇带鱼 → 之后所有局的奖池里都可能出现它 |
| **永久成长** | 仅图鉴带来的**小额**全局加成 | 是 | 图鉴完成度每 20% 给 +2% 金币，**总上限 +10%** |

> **铁律：永久解锁只能解锁内容，不能解锁强度。**
> 卖鱼的钱只能在**本局内**花。若允许跨局买永久数值，第 20 局会无聊到爆，肉鸽的重玩动机当场失效。

用户提出的"一开始只能钓小鱼 → 卖鱼 → 解锁新岛屿（新鱼 + 商店种类增加）"天然落在**内容池**这一侧，方向正确。落地时拆成两跳：

1. **本局内**：达标即进入下一座岛（临时，下局重来）
2. **跨局**：该岛被"通关过"则其鱼种与商品**进入解锁池**，之后随机局的商店可能刷出来

岛屿与深度带对齐（复用 01 第 3.6 节的深度带定义）：

| 岛 | 深度范围 | 主要稀有度 | 解锁条件（待细化） |
| --- | --- | --- | --- |
| 岛 1 浅滩 | 0–25 m | Common / Uncommon | 初始 |
| 岛 2 礁坡 | 0–50 m | + Rare | 单局渔获价值 ≥ N1 |
| 岛 3 断崖 | 0–80 m | + Epic | 单局渔获价值 ≥ N2 |
| 岛 4 深渊 | 0–100 m+ | + Legendary | 单局渔获价值 ≥ N3 |

解锁门槛用"渔获价值"而非"分数"，目标是钓鱼语义，玩家不必理解第二套数值体系。

**关卡形态定稿：教学关 + 1 个有目标值的正式关。不做无尽关。**

理由：无尽关没有"完成"判定，试玩 5 分钟体验不到闭环；而"有目标值 → 达成 → 结算"能完整展示 目标系统 / 状态机 / 事件流，这正是题目第 1 条最好的展示位。无尽模式作为 P3 之后的可选扩展。

# 八、藏品叠加约束

背包英雄类产品最常见的死法是"藏品效果互相不知道能不能叠加、谁先算、能不能改规则"。现在就定死：

> **规则：所有藏品只能修改 `IFishingStats` 的字段，不得引入任何新机制。**

| 允许的藏品效果 | 禁止的藏品效果 |
| --- | --- |
| `LineLength += 8` | "每 3 潜送一条鱼" |
| `TensionMax *= 1.25` | "有 20% 概率免疫断线" |
| `LurePull += 0.3` | "解锁双钩模式" |
| `CoinBonus += 0.1` | "把白品质鱼升级为蓝品质" |

想加新机制的东西，走**钓竿本体**（它有配件槽）或**饵料**（它是消耗品，天然可承载一次性规则）。藏品只负责数值。

配套约束：

- 同类字段**加法优先于乘法**；必须用乘法时，字段名以 `Mult` 结尾，聚合阶段统一先加后乘
- 每个字段声明 `Min` / `Max` 硬边界（如 `CoinBonus` 锁 0.6），聚合后一次性 clamp，防止叠加爆炸
- 藏品不写"触发时机"，任何需要监听事件的物品都不是藏品，归入饵料或钓竿配件

# 九、分阶段落地

每阶段结束都是一个**可提交、可玩、可讲的完整物**。这是为了对冲一个真实风险：题目第 1 条考的是工程能力，半成品肉鸽的得分大概率低于完成度高、结构干净的钓鱼游戏。

| 阶段 | 内容 | 可交付判定 | 对应题目考点 |
| --- | --- | --- | --- |
| **P0** | 核心钓鱼闭环（01 的 M0–M2）+ `IFishingStats` **以默认值实现** | 单局能下潜、能断线、能出水结算 | 状态模式、策略、对象池、MVC |
| **P1** | 背包网格 + 旋转 + 合成 + `IFishingStats` 由背包驱动 | 摆放/旋转/合成可玩，改背包后下潜参数**真的变了** | **数据结构主战场**：位图、形状表、规则表 |
| **P2** | 商店 + 每 3 潜三选一 + 金币经济 | 完整 3 潜循环，build 有成长曲线 | 权重采样、责任链、策略、数据驱动 |
| **P3** | 图鉴 + 永久解锁池 + 存档 + 岛屿分层 | 跨一局验证"内容池扩大、强度不扩大" | 序列化、版本兼容、存档迁移 |

**P0 就必须把 `IFishingStats` 立起来**（哪怕所有字段都是常量）。否则下潜层会散落一堆硬编码深度/条数上限常量，P1 接背包时全要返工。
