## 一、0.75 取证的结论

`+0.75 条载量` 不来自装备池，来自 **重载布（cloth_cargo）剪成 I 形（3 格）**：

- `ClothCatalog.asset` → `cloth_cargo` → `BuffList[0]`：`ModType: 2`（MaxCarryCount）、`PerCell: 0.25`、`Cap: 1`
- 它的形状池是 `block_4 / line_3 / slab_6`，`line_3` 就是 3 格 → `0.25 x 3 = 0.75`
- `BackpackFishingStats.MaxCarryCount` 里写的是 `Mathf.FloorToInt(Mathf.Max(0f, bonus))` → **0.75 取整 = 0**
- 这块布的上架价 = `18 x 3 x 1.9 = 103` 金币（另有 +-10% 浮动）

也就是说：**花 103 金币（第一回合大半的收入）买一块布，负载一分没涨，另外什么也没给。** 玩家只能在卡面上看到 `+0.75 条载量`，进背包后静默归零。

`cloth_cargo` 的 `BuffList` 里**只有这一条 BUFF**，所以 3 格版重载布是整件作废。

同类受害的还有 **满篓布（cloth_harvest，珍罕）**：`PerCell: 0.2`，形状池只有 `block_4 / corner_3` → 单块给 0.8 或 0.6 → 同样 floor 成 0，要买满两块才 +1，而它一块卖 270~360 金币。区别是 `cloth_harvest` 还挂了卖价（ModType 4，`0.012/格`）和诱鱼（ModType 3，`0.02/格`）两条线，不算全废，但卡面上最醒目的那条「条载量」是实打实的零。

根因是一条设计错位：**负载是全工程唯一被取整成整数语义的能力线，而布料层的 BUFF 全都按「每格给一个小数」建模。** 只要负载线来自布，就必然出现「凑不满就吞掉」。

## 三、表 B：重规划

三条设计原则：

1. **整数线不再走每格小数** —— 负载线的 BUFF 必须写成「整块定额 +1」，卡面显示 `+1 条载量`，进背包就是 +1
2. **同线双件必须靠占格差异化定价** —— 紧凑件卖贵、大件卖便宜，让「格子换数值」成为真取舍（对齐 03 第 2.2 节立身之本）
3. **每一档都必须严格强于上一档**，且封顶要留余量，不让后续商品变废纸

## 四、合成（Crafting）计划

### C1 规则：为什么必须是 2 合 1，不是 3 合 1

| 门槛 | 数值账 | 凑齐概率 | 结论 |
| --- | --- | --- | --- |
| **3 合 1** | 3 x 80 = 240 金币换 1 件定价 200 的 T2，**明亏**，只有「腾 2 格」收益 | 货架 4 格、装备池 14 件、同面货架去重（`m_takenKeys` 只在 `RollStock` 清空）→ 三件同款只能跨三回合撞，8 回合内几乎不可能成型 | 做出来像个摆设 |
| **2 合 1（推荐）** | 2 x 80 = 160 金币换 200 档，**赚 40 金币 + 腾 1 格** | 同款跨两回合撞上的概率约 3~4 倍于三件 | 玩家真的会用 |

### C2 数据：规则表 SO（对齐 03 第 5.2 节「规则表驱动，禁 if-else 硬编码品质链」）

`Assets/Data/Backpack/CraftRules.asset`（新建 `CraftRuleSO`），一个 SO、一条数组：

```
CraftRuleSO
  Rules: List<CraftRule>          // 现在就两条，将来加布的合成也是往这里追加
    CraftRule
      RuleLabel        string            「装备升档」「布料提稀」
      InputKind        BackpackDefKind   Item / Cloth
      MatchMode        enum              SameIdAndTier / SameRarityTier
      InputCount       int               2
      OutputTierDelta  int               +1
      OutputShapeMode  enum              InheritFromLargest / Redraw
      CoinCost         int               0
```

两条初始规则：

| 规则 | 输入 | 输出 | 封顶 |
| --- | --- | --- | --- |
| 装备升档 | 2 件同 `ItemId` 同 `Tier` | 同 `ItemId`、`Tier + 1`，形状与数值走 `TierShapes/TierValues` 新档，占格取两件中较大者 | `Tier 3` 封顶（金档不做，见 C5） |
| 布料提稀 | 2 块同稀有度的布（不要求同色） | 高一稀有度的随机布，形状在新布的.shapeList 里重抽 | `珍罕` 封顶 |

布的第二条规则顺带解决了两件老大难：**空白布有了出路**，以及「买错一块废布」的止损。

### C3 落点：不新建面板，不代码生成 UI

| 项 | 做法 |
| --- | --- |
| 入口 | `Assets/Prefabs/UI/UIShopPanel.prefab` 里**手工加**一个 `Btn_CraftAll`（放在暂存架 `Panel_Storage` 那一排上方），照你说的走预制体，不要动态生成 |
| 提示 | 商品/存放物视图的预制体里加一个默认隐藏的 `Img_CraftBadge` 角标，够 2 件同款时点亮 |
| 反馈动画 | 直接复用已有的 `flyToStashCoroutine` 那套补间（`UIShopPanel.cs:973`），把被吞的那件飞到留下的那件位置并缩小淡出，产物播一个 0.1s 弹放 |
| 结果落点 | 优先落在两件中锚点更靠上的那件的格位；产物变大放不下 → 原位扩展；再放不下 → 进暂存架；暂存架也满 → **整笔不执行**并提示「格子不够」，绝不吞东西 |

「合成前可能得先腾格子」这一条是故意的 —— 它让合成和摆格子互相咬合，正是这个玩法的核心取舍。

### Flat 模式说明（Q1）

现状：`ClothBuffEntry` 只有 `ModType / PerCell / Cap` 三个字段，取量写死在 `ClothEntry.ValueFor` 里 `return buff.PerCellValue * cells;`，负载再被 `Mathf.FloorToInt` 夹一次，3 格的 0.75 就没了。

Flat 模式就是给这条 BUFF 加一个「计价方式」开关：

| 计价方式 | 含义 | 用在哪些线 |
| --- | --- | --- |
| `PerCell`（默认，现在的行为） | 每占一格给多少，格越多给越多 | 线长、收线、诱鱼、卖价、横移、钩径…… 所有允许小数的线 |
| `Flat`（新增） | 这块布不管剪成几格，都固定给这个整数 | 只有负载（`ModType 2`）这种「取整才有意义」的线 |

```csharp
// 改动只有两处，约 15 行
public enum ClothBuffMode { PerCell, Flat }

public float ValueFor(ClothBuffEntry buff, int cells)
{
    if (buff == null) return 0f;
    return buff.Mode == ClothBuffMode.Flat ? buff.FlatValue : buff.PerCellValue * cells;
}
```

前后对比：

| 布 | 形状 | 现在（卡面 → 实际） | Flat 后 |
| --- | --- | --- | --- |
| cloth_cargo | 4 格 | +1 → +1 | +1 |
| cloth_cargo | 3 格 | +0.75 → **+0** | **+1** |
| cloth_cargo | 6 格 | +1 → +1 | +1 |
| cloth_harvest | 4 格 | +0.8 → **+0** | **+1** |
| cloth_harvest | 3 格 | +0.6 → **+0** | **+1** |

两个顾虑：

- **定价要不要跟着改？不用。** Flat 只让「负载这一条线」不随格数变，但布的本职是给背包铺出新格子，铺 6 格就是比铺 3 格值钱，所以 `基准价 × 占格数 × 稀有度系数` 照旧，大件布该贵还是贵，玩家不吃亏
- **方案 X 为什么不行。** X 是靠把 `PerCell` 调成 0.5 再删掉 3 格形状来凑整数，形状池被「只能是偶数格」绑死，将来往形状库里加任何奇数格异形就会重演一次 0.75；而且卡面还是「每格 0.5」这种玩家看不懂的口径

### Flat 落地后仍要配一道校验

`ClothCatalogSO` 校验时对 `ModType == MaxCarryCount` 的条目断言：`Flat` 线的 `FlatValue` 必须是整数，且卡面显示值必须等于实际生效值。不满足直接在编辑器 `Debug.LogError`，不留运行时静默吞。

### 一条新发现的连带账（开工前定死）

`BackpackFishingStats` 的聚合口径是 `Mathf.Max(0, Mathf.Min(itemSum, cap)) + clothSum`，**布料那份完全绕过装备封顶**。所以 Q2 把封顶抬到 3 之后：

- 装备负载线最高 +3，布料负载线（`cloth_cargo` Cap 1 + `cloth_harvest` Cap 1）另加 +2
- 基准 3 条 → 理论上限 **8 条**，一次下潜捞 8 条会把 11 号归档「负载砍档」的意图整个推翻

建议按「装备与布料一起算，负载总线封顶 3」落地：布料那份也吃 `CarryCountBonusCeiling`，即 `Mathf.Min(itemSum + clothSum, cap)`。这样卡面「负载已满」的判定口径和实际生效口径一致，不会出现「显示没满但已经被夹住」。若要保持布料那份独立绕过封顶，那就把 `cloth_cargo` / `cloth_harvest` 的 `Cap` 各压到 0.5 以下，但那条会被取整吞掉，等于绕回原 bug，不推荐。
